# Rubric: is this plan ready to post and build from?

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| Diagnosis is grounded in the repro evidence | The plan's stated cause, read against the repro-evidence block's steps, artifacts, and control runs | Pass if the stated cause is the one the repro evidence's controls actually isolate (a control run that changes only the suspected variable and the behavior tracks it), or one the thread already identified and the evidence is consistent with. Fail if a control run in the repro evidence rules the stated cause out (the behavior persists, or differs, in a way the claimed mechanism cannot explain) and the plan does not address that control. | required |
| The change is one bounded fix | The plan's scope/approach section, read for what it commits to building now (not what it defers) | Pass if the described change is one cohesive fix addressing only the issue's defect, touching only the site(s) of that one bug pattern (multiple sites of the *same* underlying defect are still one fix). Naming related work as an explicit, out-of-scope deferral does not fail this check. Fail if the approach itself commits to building more than one substantial, separable piece of work beyond the one defect as part of what will be done now — a rewrite, an unrelated version/dependency bump, a new abstraction layer, a new feature, or a new CI system riding along with the fix. | required |
| A stranger could start executing it | The plan's named files/locations and its diagnosis/approach section (not its risk/unknowns section) | Pass if the diagnosis and approach commit to a specific mechanism, subsystem, or area (a named file, module, or code path) and an ordered sequence of what will change there, sufficient for someone who has never seen the plan to start work without asking the author anything. A single exact-implementation detail honestly flagged as unconfirmed (an exact function name, an exact line, the precise layer within an already-named area) does not fail this check when it appears as a stated risk/unknown alongside an otherwise fully committed approach — that is honesty, not indecision. Fail if the diagnosis or approach section itself poses the core decision as an open question — which subsystem or approach to use is not yet chosen ("investigate the input stack, not sure which layer is responsible", "upstream or vendored, whichever is easier", "maybe also check other linters while at it" as a stand-in for scope), or no files/locations are named at all. | required |
| The test plan is decisive | The plan's test plan, read against the repro evidence's own steps and artifacts | Pass if the test plan names a specific, observable outcome tied to the repro evidence (re-running the repro's own steps/command and checking a named exit code, output, or artifact; a named timing threshold; a named regression case). Fail if the test plan is a subjective feeling ("should feel fast", "nothing else should feel broken") or a broad action with no assertion about the fix itself ("run the full test suite" with no named expected outcome for the change under test). | required |
| Confidence matches what the evidence shows | The plan's stated certainty (diagnosis, approach, risk section) read against the repro evidence and what is actually still open | Pass if every confident claim is backed by something the repro evidence or thread actually shows, and remaining unknowns or risks are named as such rather than glossed over. Fail if the plan asserts something as settled or verified that the repro evidence does not actually establish, or if a risk plainly visible in the repro evidence goes unmentioned while the plan otherwise reads as fully certain. | required |
| The plan comment engages the thread and the repo's conventions | The plan comment, read against the thread highlights for explicit maintainer direction, and against the repo-facts contribution-policy line for an AI-disclosure requirement | Fail if any of: the thread highlights contain explicit maintainer direction (a named cause, a requested test, a stated preferred approach) and the plan comment neither adopts it nor explicitly explains why it takes a different path; or the policy text contains an explicit disclosure requirement ("must be disclosed", "stating the tool used") or a stated ban on a specific AI-involvement category, and no comment in the package discloses AI assistance. Pass otherwise: no explicit maintainer direction exists, or the comment engages it; and the policy is silent, asks only for human-voiced comments, or a comment already discloses as required. | required |

## Verdict rule

Accept if and only if every `required` check passes. `unclear` on any
required check counts as fail. There are no `preferred` checks this
round; every family named in the lecture gates the verdict, because a
plan that fails any one of them is not one a stranger should start
building from.
