# Rubric: is this pull request ready to submit?

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| Diff stays inside the plan | The diff's changed files and hunks, read one by one against the plan-context block's scope pair (in scope / not in scope), named files, and any deviation note | Pass if every changed file and every hunk serves the one fix the plan names, or falls under a recorded deviation note. Fail if any hunk does something the plan never mentions or scopes out (a second fix, a rename pass, a new flag or config option, a rewrite of a function the plan does not name, a dependency bump), however small, unless a deviation note covers it. Extra tests and a changelog entry for the planned fix are inside the plan. | required |
| Description promises only what the diff delivers | Every factual claim in the PR description ("implements the plan exactly", "no changes beyond", "docs now document X", "fixes A and B"), read against the diff and the plan's deliverable list | Pass if each claim is true of the diff, and every plan deliverable missing from the diff is disclosed in the description or in a deviation note (deferred, dropped, or limited). Fail if the description claims fidelity or a deliverable the diff contradicts or lacks (claims "exactly as planned" over extra hunks, or claims a docs update the diff does not contain), whether the PR does more or less than it says. | required |
| Test evidence is decisive | The test-evidence section, read against the plan's test plan and the repro evidence's own steps | Pass if (a) the plan's primary repro (the scenario that fails today) is shown before and after with pasted output or a pasted observable value (output, exit code, count) on the path the fix changes, and the expected-after is stated; (b) every other scenario the plan's test plan names (a control, a second failure mode) is at least reported with its outcome, in pasted output or a stated result; and (c) if the plan's test plan or the repo's contributing docs name a test suite or check command, its outcome is stated. A failing or skipped check disclosed with its reason passes. Fail if the evidence is an assertion ("tested locally", "tests pass", "verified working") with no observable result; shows only a control or the unchanged path in place of the primary repro; never mentions a scenario the plan's test plan names (silence, not a stated "not run"); or omits the suite or check the plan or docs name. | required |
| Diff is free of debris | The unified diff and the commit list | Pass if the diff has no leftover debug output (print or log statements added for debugging), no commented-out code, no dead or unused code added, no whitespace or reformatting churn on lines unrelated to the fix, no re-printed or duplicated blocks, and no unresolved TODOs added by this PR. Mechanical churn around a correct fix still fails. Fail on any of these. Commit messages such as "wip" or "cleanups while debugging" are context, not a failure on their own. | required |
| Repo's template and checklist asks are met | The repo-facts block's pull-request line (live: `.github/PULL_REQUEST_TEMPLATE.md` and the contributing guide), read against the description and the diff | Pass if every section the template names has real content in the description (not a placeholder, not left blank), the issue is referenced the way the template asks (for example a `Closes #N` line), checklist items that apply are checked or explained, and any artifact the repo states as required for this kind of change (a changelog or release-notes entry, a test) is present in the diff. Fail if a stated required section, link, checklist, or artifact is visibly missing or ignored. Where the repo states no template, pass if the description names the issue and the change. | required |
| AI-use disclosure matches the repo's policy | The repo-facts contribution-policy line (live: `CONTRIBUTING.md`, `AI_POLICY.md`, the PR template's disclosure section), read against the PR description | Fail only if the policy text contains explicit disclosure language ("must be disclosed", "stating the tool used and the extent of the assistance") or a stated ban on a category of AI involvement, or the PR template has an AI-disclosure section, and the description contains no disclosure of AI assistance. Pass otherwise: the policy is silent, asks only for human-voiced writing or human understanding, or the description already discloses in the author's own words. | required |

## Verdict rule

Accept (submit) if and only if every `required` check passes. A check
graded `fail` or `unclear` holds the PR (reject); `unclear` counts as a
fail. A disclosed shortfall is not a failure by itself: it fails a check
only if the description claims otherwise or the plan's deviation notes do
not cover it. There are no `preferred` checks.
