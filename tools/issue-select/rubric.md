# Rubric: is this a good first issue?

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| Maintainer alive | The "last 5 default-branch commits" dates and the "maintainer first-response sample" in the repo-facts block (live mode: the repo front page's recent commit list and a scan of 5 recently-updated issues for owner/member/collaborator replies) | Pass if at least one of the last 5 default-branch commits is dated within 90 days of the capture date (eval) / today (live), OR the maintainer first-response sample shows at least one owner/member/collaborator reply within 30 days of that issue's open date. | required |
| Repo in use | The "archived:" flag, "last push to any branch", and "latest release" lines in repo facts (live mode: the archived banner, the front page's newest commit date, and the Releases box) | Fail if archived is yes. Otherwise pass if last push to any branch is within 180 days of the capture/live date, OR the latest release is within 365 days of the capture/live date. | required |
| Scope fits a newcomer | The issue body and the full comment thread | Fail if any of: the issue explicitly says its listed sub-items are meant to be split into separate issues or PRs, or is itself a tracking list of otherwise-unrelated items (a meta/tracking issue); the thread shows the design is still being debated with no maintainer decision settling it; a maintainer or the issue opener explicitly states in words that the fix requires touching core internals or a large refactor (your own estimate of difficulty does not count — only a stated claim in the text does). Also fail if the issue is a pure usage/support question ("how do I get this to work?") with no proposed change, or if it is a feature request that leaves a key design/product decision unresolved (marked "TBD", "if needed", or similarly undecided) and no maintainer has endorsed or scoped it (no maintainer comment, and the opener is not a maintainer/owner/collaborator). Also fail if the issue's linked-PR history shows two or more closed, unmerged attempts across different contributors or years — a repeated pattern of abandoned attempts is telling you the real difficulty exceeds what a first issue implies, whatever the label says. Pass a single cohesive change that happens to touch several files, steps, or optional/alternative approaches in service of one named problem (e.g., a bug report naming multiple possible causes or fixes, or a new docs page plus updating its cross-references) — that is one bounded piece of work, not an umbrella, however many parts it lists. A terse body, an acceptance-criteria checklist, or an undocumented bug report can still pass — grade the size of the work, not the polish of the writeup. A single old closed/abandoned linked PR by itself does not fail this check. | required |
| Nobody already on it | The "this issue: assignees" and "linked PRs" line in repo facts, plus claim comments in the thread (live mode: the Assignees box, the Development box's linked PRs, and the thread) | Fail if any of: the assignees list is non-empty; any linked PR is listed as open; the thread has a claim comment ("I'll take this", "working on this", "can I work on this") posted within 12 months of the capture/live date with no sign of abandonment. A claim older than 12 months, or one accompanied by a closed/abandoned linked PR or a bot's stale-issue mark with no further activity from the claimant, does not fail this check. | required |
| Contribution policy allows this workflow | The "contribution policy" line in repo facts (live mode: `CONTRIBUTING.md`, `.github/`, or a dedicated `AI_POLICY.md`/`AI_USAGE_POLICY.md`) | Fail only on an outright ban on AI-generated code or documentation. Conditions (disclosure, personal understanding, testing, human review) pass. Silence (no stated policy) passes. | required |
| Has a "good first issue" style label | The issue's labels line | Pass if the issue carries a label such as `good first issue`, `good-first-issue`, `help wanted`, or similar | preferred |

## Verdict rule

Accept if and only if every `required` check passes. Any `required` check
graded `fail` or `unclear` rejects the issue. `preferred` checks never
change the verdict; they only rank issues that are accepted, best fit
first.
