# Rubric: is this reproduction package ready to post?

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| Environment recorded | The repro report's environment line(s): OS/platform, the tool or library version under test, and how it was installed/run | Pass if the report names the OS or platform, the exact version of the tool/library being tested, and (where relevant to the issue) the install method or build profile. Fail if there is no environment record at all, or if the issue's behavior is known to depend on a detail (e.g. OS, driver, build profile) the report omits entirely. | required |
| Steps are complete and match the issue's trigger | The repro report's steps, read against the issue's exact reproduction recipe (command, flags, input, syntax) | Pass if the steps a stranger would follow use the same triggering condition the issue names (same flags/syntax/input shape), starting from a stated starting state that a stranger could actually obtain or recreate, with no undisclosed substitution. Fail if the steps swap in a different command, flag, syntax, or input than the issue's own trigger without saying so (an "operator swap"); skip the specific condition the issue says is required to trigger the bug; or depend on a private or unshared resource (a company repo, an internal config file, a dataset) that the report says it cannot share and that a stranger has no way to obtain or reconstruct, even when the reporter asserts it matches the issue's shape. | required |
| Behavior shown matches the issue, or the report is an honest miss | The artifact (output excerpt, log, error text, screenshot) in the repro report, read against the exact behavior/error the issue describes | Pass if the shown artifact demonstrates the same symptom the issue describes (same error type/message shape, same observable failure), not a different or milder one. An honest cannot-reproduce also passes this check if it shows what was actually run, states plainly that the reported behavior did not occur, and names a concrete difference between the attempt and the issue's setup (version, environment, config) that plausibly explains the miss. Fail if the artifact shows an adjacent or different failure (wrong error type, a graceful validation error instead of the reported crash, the target program still alive when the issue reports a crash) and the report narrates it as confirming the issue anyway, or if an old/irrelevant version's behavior is presented as evidence about a bug reported on a different version without acknowledging the gap. | required |
| Confidence matches the evidence (honesty) | The report's claims of certainty, read against what the artifacts actually show | Pass if every confident claim in the report ("confirmed", "guaranteed reproducible", a stated root cause) is backed by an artifact shown in that same report. Fail if the report asserts confirmation, a verified root cause, or reproducibility with no shown artifact backing it (a "trust me" report), or if intensity of language ("100% confirmed", "conclusively demonstrates") substitutes for evidence rather than describing it. | required |
| Claim comment is specific and honestly scoped | The candidate claim comment, read on its own | Pass if the claim names the specific issue/behavior being investigated and promises only investigation or a next concrete step (not a fix, not a delivery date, not "guaranteed"). Fail if the claim is interchangeable boilerplate that could be pasted onto any issue ("please assign me", "I'll fix this in N days guaranteed"), asserts certainty about the cause before any investigation is shown, or is a pure "+1"/me-too with no stated intent to do anything. | required |
| AI-assistance disclosure matches the repo's policy | The repo-facts contribution-policy line (live mode: `CONTRIBUTING.md`, `AI_POLICY.md`, or `AI_USAGE_POLICY.md`), read against the candidate comment(s) | Fail only if the policy text contains one of two explicit signals AND no comment in the package discloses that AI assistance was used: (1) explicit disclosure language ("must be disclosed", "disclosing", "stating the tool used and the extent of the assistance"), or (2) a stated ban on a specific category of AI involvement (e.g. "fully AI-generated contributions are not accepted") — a ban like this requires the maintainer to know the involvement level to enforce it, so it functions as a disclosure requirement even without the word "disclose". Pass in every other case: the policy is silent on AI; it asks only that comments/code be authored or reviewed by a human in their own words (a voice/authorship rule, not a ban on any AI-involvement category) and the comment reads as first-person and specific; it welcomes AI use conditioned on human responsibility without banning any category or naming an explicit disclosure ask; or a comment already discloses. Naming a dedicated AI-policy document by itself is not a fail signal — read what that line actually asks for. | required |

## Verdict rule

Accept if every `required` check that applies passes. A claim-only draft
excludes the checks that need the repro report from the verdict (per
SKILL.md's claim-only rule); the remaining required checks still gate it.
`unclear` on an applicable required check counts as fail. `preferred`
checks never change the verdict.
